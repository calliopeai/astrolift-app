# Certification Campaign Spend

Generated by `make campaign-spend` (backend/providers/scripts/campaign_spend.py)
from `_cert/spend.py` -- do not hand-edit.

The estimate #1417 has been waiting on, for the spec 43 campaign `cert2026q3`:
the happy path on three clouds plus the 69-cell per-kind grid, each cell run
through the full lifecycle cycle 2x because the campaign's own definition of
GREEN requires an unattended second run (spec 43 §0.1 step 7).

## Read this first

**81 of 81 bookings are unpriced in dollars.** Cost figures come from the
cloud's live pricing API and never from a table in this repository
(`_sdk/cost.py`). Nothing is vendored or cached in the tree and this report is
generated offline, so it prices nothing and says so per booking rather than
filling the gap with a plausible number.

**64 of 81 bookings have no billing class at all.** `_cert/billing.py` classifies
AWS preview variants only. Every GCP and Azure variant, and every AWS variant
the campaign actually books on the happy path, raises `UnclassifiedVariant`.
That is not a reporting gap -- `check_may_run` refuses to provision an
unclassified variant, so the campaign cannot start against most of its own grid
regardless of what any estimate says.

**The most useful thing here is the shopping list.** Every cell books
`size=small` (the manifests declare no size and the provision activity
defaults it), and each driver resolves that to a concrete capacity in code. The
per-cell table below names it. Multiply by a live unit price and the estimate is
finished; that multiplication is the only step this report cannot do.

## What a real number requires

In order, cheapest first. The first two need no cloud account.

1. **Classify the grid in `_cert/billing.py`.** A table edit, offline, no
   credentials. Until it lands, the spend gate blocks the campaign and this
   report cannot say which cells dominate -- the question #1417 is actually
   asking. This is the blocking item.
2. **Fix the estimators that over-count.** `_sdk/cost_skus.py` resolves one
   catalog row per billable dimension and refuses on ambiguity. GCP's Cloud SQL
   path uses it; the AWS and Azure estimators still sum whatever their filter
   returns, which is why 37 bookings are marked approximate not exact
   (#1318). An approximate estimate is what a class C pre-flight would log today,
   and #1417 decision 2 makes that log the thing that unlocks the spend.
3. **Map the variants that have no estimator.** Azure's
   `SERVICE_NAME_BY_VARIANT` still keys on `flexible_server`, `cache`, `cosmos`
   and `files`, none of which exist in the availability matrix, and on `blob` and
   `servicebus` where the campaign books the `azure_blob` / `azure_servicebus`
   aliases. No Azure cell in the grid resolves a pricing path.
4. **Run the estimator with credentials**, once, per cell, before provisioning
   anything. That is the only step that produces dollars.

## The metered window

How long a cell holds a resource, bounded by the harness's own declared
timeouts. These are **ceilings, not expectations**: a cell that provisions in
four minutes bills for four minutes. A ceiling is the right shape for an
approval, because the approval has to cover the bad day.

| Step | Ceiling | Composed from |
| --- | --- | --- |
| BUILDOUT | 130 min | two `provision_poll` waits (app, then services) plus one deploy |
| UPDATE | 120 min | three deploys: forward, rollback, forward again |
| TEARDOWN | 45 min | one `teardown_poll` wait, floored by the 5 min deregister grace |
| **one pass** | **4.92 h** | steps 1-6 of the lifecycle cycle |
| **one cell** | **9.83 h** | both passes, because GREEN requires the second |

Read from `LifecycleRunner.provision_poll` / `.teardown_poll` /
`.include_rollback` and `CliPlatformClient.timeout_s` rather than restated, so
retuning a timeout moves this table. The five HTTP probes in VERIFY-UP and
VERIFY-UPD are bounded at 60s each and omitted: 5 min against a 5 h ceiling is
below the resolution of anything this report decides.

## Exposure, per cloud and in total

Resource-hours, not dollars: the hours are known and the rate is not. Counts
are bookings (a per-kind cell books one managed service, a happy-path cell
books four), and hours already include both passes.

| | Cells | Bookings | Hourly floor | Fixed floor | Per request | Cluster | Unknown | Metered hours | Unknown ceiling |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| aws | 24 | 27 | 5 | 4 | 3 | 0 | **15** | 88.5 | 147.5 |
| gcp | 24 | 27 | 0 | 0 | 0 | 2 | **25** | 19.7 | 245.8 |
| azure | 24 | 27 | 0 | 0 | 0 | 3 | **24** | 29.5 | 236.0 |
| all clouds | 72 | 81 | 5 | 4 | 3 | 5 | **64** | 137.7 | 629.3 |

**Metered hours** covers only the 14 bookings whose shape is known -- and every
one of them is on AWS. A tri-cloud campaign whose entire quantifiable metered
exposure sits on one cloud is not a costed campaign; it is a costed third of
one.

**Unknown ceiling** is what the 64 unclassified bookings would add if every one of
them turned out to meter hourly. It is the size of the ignorance, not an
estimate of the cost, and folding it into a single total would produce exactly
the confident wrong number this report exists to avoid.

Two categories are excluded from both columns on purpose. Per-request bookings
cost nothing measurable: the campaign publishes a handful of messages through
the fixture's `/selftest`. Cluster-capacity bookings are pods on a tenant
cluster that bills for the campaign's whole wall clock whether the cell runs or
not, so charging them to the cell would double-count a floor already paid.

## Which cells dominate

By construction the hourly-floor bookings are the whole decision: they are the
only ones whose cost moves when the campaign runs long, runs twice, or fails to
tear down. Everything else is either flat or free.

5 bookings are known to sit on an hourly floor:

| Cloud | Kind | Variant | Books at `small` | Why hourly |
| --- | --- | --- | --- | --- |
| aws | `cache` | `elasticache_memcached` | `_SIZE_TO_NODE_TYPE` = cache.t4g.micro | class C: Node-hours from creation. |
| aws | `document_db` | `documentdb` | `_SIZE_TO_INSTANCE_CLASS` = db.t4g.medium | class C: Instance-hours plus storage. |
| aws | `event_stream` | `msk_serverless` | `_SIZE_BROKERS` = 3, `_SIZE_INSTANCE` = kafka.m5.large | class C: Per-cluster hourly charge plus partition-hours. |
| aws | `graph_db` | `neptune_serverless` | `_SIZE_TO_INSTANCE_CLASS` = db.t4g.medium | class C: NCU floor bills continuously. |
| aws | `mssql` | `rds_sqlserver_express` | `_SIZE_TO_STORAGE` = 20 | class C: Instance-hours; licence included but the instance runs. |

**This list is not the answer, and the gap is the finding.** 64 bookings have no
billing class, and the ones a reader would expect to dominate are inside that
group: RDS, ElastiCache, OpenSearch, Cloud SQL, Memorystore, Azure Postgres
Flexible, Cosmos, Azure Cache for Redis. Naming them as hourly here would mean
asserting a billing shape that `_cert/billing.py` has not reviewed, which is the
same shortcut that module refuses to take when it declines to sweep an
unclassified variant into class A. The ranking arrives when the table does.

### The lever, once the ranking exists

Each cell runs 2x, so the hourly-floor set is charged twice: 4.9 h per pass,
9.8 h per cell. Two levers, neither free:

- **Run the expensive cells once.** This is the obvious saving and it is not a
  saving: REPRODUCE is what certifies a cell, so dropping it downgrades that cell
  to uncertified rather than making a certified one cheaper. Defensible only for
  a variant with no evidence of demand, which is decision 4's argument applied
  per cell instead of per class.
- **Shrink the window.** The ceiling is dominated by UPDATE's three deploys.
  `LifecycleRunner.include_rollback=False` removes two of them and cuts the
  per-cell ceiling from 9.8 h to 7.2 h, at the cost of not
  exercising rollback. The campaign exists partly to exercise rollback.

## The cost of leaving it running

The campaign's financial risk is not the run. A run is bounded by the window
above and stops. A teardown that fails is unbounded: it bills until somebody
notices, and the thing that makes somebody notice is the orphan scanner
(`_cert/orphans/`). This is that number, and it is why the scanner is not
cleanup hygiene.

If the entire grid were stranded -- every distinct booking left provisioned:

| Meter | Bookings | Accrues while stranded |
| --- | ---: | --- |
| hourly floor | 5 | yes, 120 resource-hours per day |
| fixed floor | 4 | yes, small and flat |
| cluster capacity | 5 | yes, as pods on a cluster already billing |
| per request | 3 | no; idle costs nothing |
| **unknown** | **64** | **cannot say** |

**336 resource-hours per day** accrue from the bookings whose shape is known,
and up to **1536 more** from the 64 whose shape is not. A week unnoticed
multiplies both by seven. Against that, one cell's entire certified lifecycle
is under ten hours.

Two properties of this tree make the stranded case more likely than it sounds,
both already recorded on #1471: the campaign tag never reaches a resource
because `_provision_sync` builds its `ProvisionSpec` without `tags=`, and two
GCP drivers drop `spec.tags` even when populated. A scanner that cannot see a
resource reports clean, which is the failure mode that turns a bounded run into
an unbounded bill.

### What the campaign puts on the clusters

Aggregate pod requests across every committed manifest, per cloud:

| Cloud | Replicas | CPU requested | Memory requested |
| --- | ---: | ---: | ---: |
| aws | 26 | 2.6 vCPU | 3.25 GiB |
| gcp | 26 | 2.6 vCPU | 3.25 GiB |
| azure | 26 | 2.6 vCPU | 3.25 GiB |

Small on purpose -- the fixture is a web app, not a benchmark. The contrast is
the point: a tenant cluster is an hourly floor that dwarfs what the campaign
puts on it, so it costs what it costs whether the grid runs fast or slow.

These are the manifests' own workload pods only. An in-cluster managed service
places pods of its own, sized by the driver rather than by the manifest, and
not all of them are small. Those show up per booking in the table at the end,
under `Books at`, and are not summed here.

What the existing machinery would return per booking if it were run with
credentials. None of these is a price; they rank what a live run would get back.

| Verdict | Bookings | Meaning |
| --- | ---: | --- |
| exact | 4 | a SKU plan resolves one catalog row per billable dimension |
| approximate | 37 | the estimator sums whatever its filter returns; over-counts by construction (#1318) |

| n/a (in-cluster) | 5 | no managed-service SKU exists; it is cluster capacity |

4 of 81 bookings would come back with a number worth acting on, all of them
Cloud SQL, which is the one variant family `gcp/cost_plans.py` covers. Spec 43
§4.3 says a cell the preview cannot price is a finding rather than a rounding
error; on those terms this table is a list of findings.

## The floor this ledger does not cover

Spec 43 §4.2 stands up a control plane on each cloud through the installer
agent and registers a tenant cluster per cloud before the first cell runs. Those
six things bill for the campaign's entire wall-clock, not per cell, and they are
almost certainly the largest line on the bill.

They are absent here because nothing in this tree describes their shape. The
installer targets live in another repository, and the `compute:node_hour`
estimator that would price a cluster's nodes has no caller in this repository
and no control-plane equivalent at all. Estimating them from this side would be
guessing, so the ledger reports the per-cell exposure it can derive and names
this as the missing term rather than quietly omitting it.

Practical consequence for the decision: campaign spend is roughly
`(fixed floor per hour) x (wall-clock hours) + (per-cell exposure above)`. The
second term is bounded and reported; the first is unbounded in wall-clock, which
is the argument for spec 43's own instruction to tear down at the end of each
day's run rather than at the end of the campaign.
